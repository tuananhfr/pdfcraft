# ERPCons changes

This branch (`erpcons`) is the ERPCons Văn phòng fork of [PdfCraft](https://github.com/storytold/pdfcraft), based on PdfCraft by the ArtCraft team, licensed MIT OR Apache-2.0 (see `LICENSE-MIT`, `LICENSE-APACHE`, `NOTICE`). Changes from upstream `main` (Apache-2.0 §4b):

- (web) Access modes of the office shell's `window.erpHost` v2 (`erpcons-office/docs/erp-host.md`, "v2"; `crates/ui-egui/src/online/{access,preserve,user}.rs`, `crates/ui-egui/src/access_guard.rs`, `crates/engine/src/limits.rs`): the app takes `erpHost.version` 1 or 2, and 1 works as before. With 2, `open(doc)` reads `mode` (`edit`, `comment` or `view`; absent is `edit`, a word the app doesn't know counts as `view`), `canDownload` (absent is `true`) and `preserveView`, and the app also registers `setMode(docId, mode, canDownload)` and `setUser(user)`. View and comment (comment is view for the content in this phase) put session limits on the document in the engine (`Session::set_limits`), never written into the file and lifted by `setMode` without reopening, the document and its undo history intact: edits, undo, redo, revert, signing, OCR and scripts that would change the document return `EditError::ViewOnly`, and the editing commands, tools, quick bar, form fields, Delete, paste and files dropped on the page grid are greyed or refused with "Tài liệu này chỉ được mở để xem." (also the document's notice bar). Nothing goes to the shell for a document opened that way: no `dirty` change, no AutoSave, no `flush` item, and Save (a Save queued before the switch too) only says so. A switch down to view or comment first commits what is still being typed (a form field, Edit text, Add text, the Fill & Sign text box, a comment being written or edited in the Comments panel; `crates/ui-egui/src/inline_edits.rs`), each as one undo step, as its own commit would; a value its field refuses or text the fonts can't draw stays in its editor. A document switched while unsaved keeps its edits and stays unsaved, AutoSave and Save stay off for it, and only `flush` hands it to `save` (reason `flush`, rules 1–6) until it is `saved` or stopped by a conflict or a non-retryable failure. Navigation, zoom, find, copy, Save As, export and print stay. `canDownload: false` greys Save As, Share, Print, every Export, the snapshot tool, Copy pages, Extract, Split, Reduce file size, Optimize PDF and the comment and form data exports, and refuses copying text, images and comment text ("Tải xuống, in và sao chép đã bị tắt với tài liệu này."); `edit` keeps editing. `preserveView` gives the version that replaces a tab the page (clamped to its pages), the zoom and the page display the tab had, and on a phone keeps the wide-window zoom for later. `setUser({ id, name })` makes the account's name the author of new comments, markups, replies and redaction marks while the settings keep the local name, and `setUser(null)` brings the local name back. In view and comment, All tools greys the tool groups that would change the document (a group with something refused and nothing left but viewing: Edit a PDF, Fill & Sign, Organize pages, Comment, Scan & OCR, Protect, Redact, Prepare a form, Stamp, Use a certificate, Measure and the like), saying why on hover, and they don't open; Export, Create, Combine, Compress, Compare and other tools that only view the document or make a new file stay (with downloading off, the export tools grey instead). Comment mode stays view-only on the web for now and says "Nhận xét trên web sẽ có sau, hiện chỉ xem được" wherever view mode says "Tài liệu này chỉ được mở để xem.". With `erpHost` v2 the app's own File ▸ Share… is not offered: the shell's Share is the only one (the free web build and `erpHost` v1 keep it). Tests: `crates/engine/tests/limits.rs`, `crates/ui-egui/src/online/access_tests.rs` (every edit family, keys, paste and drop refused in both modes; `setMode` both ways; downgrades committing form typing, Edit text, Add text and a comment being written, then `flush`; `canDownload`; `preserveView`; `setUser`; All tools; Share; the comment-mode notice). The desktop app is unchanged.
- (web) Online documents through the office shell's `window.erpHost` v1 (`erpcons-office/docs/erp-host.md`; `crates/ui-egui/src/online/`, `apps/pdfcraft-web/src/erp_host/`), checked once at start and never together with `?host=parent`: the app registers `open`, `flush` and `acknowledged` with `erpHost.ready`; a document `open` hands in (format `pdf` only) opens under its title and is reported with `opened(docId, ok, reason?)` (a password prompt is `ok`; a refused format is not, with reason `unsupported`, nor an unreadable file or one over the memory budget, with reason `parserFailed`: keys of the shell's intake messages; a cancelled password prompt reports `closed`). Save (Ctrl+S, "Lưu", a save prompt's Save, Save all) of such a document calls `erpHost.save(docId, bytes, { revision, reason: "manual" })` with the bytes Save writes today (incremental, Fill & Sign flattened when that preference is on), never a picker; AutoSave sends `reason: "auto"` 3 s after the last edit and at least every 30 s while edits keep coming, without flattening; `flush()` hands the working file of every such document whose revision is not acknowledged to `erpHost.save` (`reason: "flush"`, after a save of it in flight) and resolves once each has been handed over, without waiting for the answers, or after 10 s. One save per document is in flight; later ones wait and coalesce into one save of the newest revision. A document counts as saved only on `saved`, and only if it is still the revision that was sent (edits made meanwhile stay unsaved and go next). `conflict` stops AutoSave and flush for that document and is never retried (Save is still the user's); `offline` and a retryable `failed` keep the document unsaved and AutoSave going without resending that revision; `acknowledged(docId, revision, version)`, the shell's own retry of such a revision stored, counts as `saved` for that revision (same rule; one older than the last acknowledged revision, or for a document not open, is ignored); a non-retryable `failed` stops AutoSave and shows the shell's message as a failed save (notice and the tab's "Save failed"). A signed document is never sent without the existing "Save changes after signing?" confirmation: AutoSave stays off for it (a notice says so once: "Tự động lưu đã tắt với tài liệu đã ký. Chọn Lưu để lưu thay đổi.") and flush sends it only as far as such a Save confirmed. `dirty(docId, bool)` is called when the document's unsaved state changes, `closed(docId)` when its tab closes (not when a new `open` of the same document, as after a conflict, replaces the tab in place, and answers to the replaced one's saves are ignored). Such documents never go to `erpDrafts` nor to Reopen Closed Tab, and the page's own reload warning counts only documents from the device (the shell guards the others); Save As, export, share and print stay local (Save As writes a copy and leaves the document the server's, unsaved and under its title). Script trust is per document as for any file. Documents opened from the device and the desktop app are unchanged. The log scan (`tests/log_privacy.rs`) now also flags a logged `title` or `doc_id`.
- (both) Acrobat JavaScript and XFA scripts never run silently (`crates/engine/src/js.rs`, `crates/ui-egui/src/script_bar.rs`): JavaScript is off by default, in the engine, the apps, the CLI and automation alike. A document with scripts (document-level JavaScript, XFA template scripts, JavaScript on fields, buttons or widget actions; OpenAction scripts never run and don't count) opens without running any and shows a bar over its pages, "Tệp PDF này chứa JavaScript. Script chưa được chạy." with "Cho phép với tệp này" and ×. Allowing commits any field still being typed in, then trusts that document for the session only (never saved): one without unsaved changes or undo history reopens in place so its XFA initialize and calculate scripts run as on opening (on-open print and save requests stay dropped), one with either keeps its entries and undo history and runs scripts from the next change; other documents, a second copy of the same file and a closed tab reopened stay blocked, and a file reloaded after it changed on disk is not trusted again until allowed. A button or calculation that would have run says so on the bar (which comes back once if it was closed) instead of doing nothing silently, and so does the JavaScript console or an Action Wizard Run JavaScript step blocked on a document without scripts of its own, whose bar then offers to allow them; AF format, validate and calculate calls keep working natively, as do the one-line button actions read without a script engine (`app.alert`, `app.launchURL`, which still asks first, `buttonImportIcon`). Preferences ▸ JavaScript is now "Always allow JavaScript in PDFs (don't ask)", stored under the new key `javascript_always`: the old `javascript` key (on by default) is ignored, so everyone starts with it off. Automation's `js_enabled` sets the same preference.
- (both) Logs no longer name the user's documents (`crates/ui-egui/src/log_safe.rs`): a document's name, path or URL is logged as its extension and size (".pdf (12345 bytes)"; the web `?file=` fetch failure, a closed document too large to keep, Show in folder), and the app's own folders (settings, recovery, log file, fonts, control file, single-instance socket, portable mode) with the home folder as `~`. `--<flag> <value>` errors no longer echo the value, which may be a document path an unknown flag swallowed. `tests/log_privacy.rs` scans `apps/`, `crates/ui-egui` and `crates/engine` (skipping only each brace-balanced `#[cfg(test)]` module) for log macros with an argument that interpolates a name, path, URL or file and is not built by `log_safe`, with an allowlist (GPU adapter names). `pdfcraft-cli` prints the paths its user typed to the terminal and is not scanned.
- (web) File ▸ Share… (`file.share`, `crates/ui-egui/src/share.rs`, `apps/pdfcraft-web/src/share.rs`): when the office shell reports `window.erpCanShareFiles("application/pdf")` true (asked once at start; never in `?host=parent` mode) the File menu offers Share…, which takes the bytes Save a copy would write (form typing committed, Fill & Sign flattening and a signed file with changes first asks "Share changes after signing?", whose Share… shares inside that click and whose Cancel does nothing) and hands them to `window.erpShare(bytes, name, "application/pdf")` inside the click; when that returns false or is missing, or the menu item or dialog button was pressed with Enter or Space, or the command ran from the palette or control channel (no pointer click, so no user activation), the file downloads instead. Sharing is an export: the document stays unsaved. No keyboard shortcut (browsers share only inside a click); hidden on the desktop and without the shell.
- (web) Files the office shell delivers by drop report how they ended through the optional `window.erpIntakeResult(name, size, ok)`: once per dropped file after it opened (or a password was asked for) or failed, `ok` false with the browser's file size when the browser could not read it, and `ok` for files dropped on Combine files, which always join the list. Encrypted files dropped together ask for their passwords one after another. Files picked with File ▸ Open are not reported; desktop builds never call it.
